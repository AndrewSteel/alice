DMS Pipeline Map

How the 16 alice-dms-* / alice-mail-* n8n workflows and 5 extractor containers hand documents to each other — every Redis key, MQTT topic, and database write, traced end to end.

20 workflows ~30 Redis keys 11 MQTT topics 8 Weaviate collections 1 Postgres table (dms-specific)

01Pipeline flow

A file's journey from watched folder to searchable, thumbnailed document. Solid arrows are MQTT hops; dashed arrows are Redis-mediated hand-offs. The nightly batch (02:00) is where classification and structured extraction actually happen — everything before it just moves and stages raw text.

02Ingestion & dispatch

Folder config lives in Postgres; everything about which file is where during a scan lives in Redis.

alice-dms-scanner

Dispatcher — does not read file contents itself
Trigger
cron 0 7-22 * * *
Reads
alice.dms_watched_folders (Postgres, active folders)
Redis
lock alice:dms:scanner:lock:folder:<id> · stats dispatch:run_start, dispatch:stats:* · reads path_to_hash, hash_to_paths:<hash>, processed for its stale-file sweep
MQTT
pub alice/dms/scanner/stats · pub alice/dms/lifecycle (delete_file, for vanished files)
Calls
fires alice-dms-path-worker per locked folder, fire-and-forget

alice-dms-path-worker

Sub-workflow only — one call per locked folder, 2h run cap
Trigger
Execute Workflow from scanner
Redis
renews/releases the folder lock · dedup processed, queued_files (Sets) · map path_to_hash (Hash), hash_to_paths:<hash> (Set) · stats scanner:stats:folder:<id>:*
MQTT
pub alice/dms/{pdf,ocr,txt,office,image} by file type · pub alice/dms/lifecycle for moves/renames · pub alice/dms/scanner/path_stats

alice-dms-lifecycle

Keeps Redis path-maps and Weaviate objects in sync on move/delete — independent of the nightly batch
Trigger
MQTT alice/dms/lifecycle
Redis
HSET/HDEL path_to_hash · SADD/SREM hash_to_paths:<hash>
Weaviate
PATCH additionalPaths / filePath · DELETE object (cascades BankTransaction children)
MQTT out
pub alice/dms/done or alice/dms/error

03Extraction & nightly storage

Five stateless extractor containers stage text; one nightly workflow does all classification and writes.

dms-extractor-pdf / -txt / -office / -ocr

Node.js / Python containers, MQTT-triggered
Sub
alice/dms/{pdf,txt,office,ocr}
Redis
RPUSH alice:dms:plaintext · dedup TTL 3600s alice:dms:<type>:processing:<field>

dms-extractor-image

Python, Ollama Vision
Sub
alice/dms/image
Redis
RPUSH alice:dms:image · if GPS EXIF: RPUSH alice:dms:geocode_pending

alice-dms-processor

The core write path — everything else just feeds this
Trigger
cron 0 2 * * *
Redis
GPU lock alice:dms:processor:lock:run (shared with 4 other workflows, see below) · drains plaintext, image, geocode_pending · updates processed, queued_files, path_to_hash · quota geocode_quota:<date> · stats run:stats
Calls
alice-dms-classify-document (2-attempt Ollama classification) → alice-dms-language-check (forces German title/summary)
Weaviate
dedup search by filePath → upsert into Invoice / BankStatement / Document / Email / SecuritySettlement / Contract; "Phase B" chunks BankStatement text → batch-inserts BankTransaction children; separate branch inserts Image + geocodes via Geoapify
MQTT
pub alice/dms/done (success) or alice/dms/error

alice-dms-thumbnailer

Workflow + FastAPI container (port 8004)
Trigger
MQTT alice/dms/done
Does
fetches source (NAS file, or Weaviate Email body) → POST container /generate → PATCH thumbnail_path on the Weaviate object
MQTT out
pub alice/dms/thumb_error on failure

04Mail side-channel

Email skips the extractor stage (body text is already available) but attachments deliberately rejoin the normal folder-scan path.

alice-mail-sync

Trigger
every 1 min
Postgres
alice.imap_mailboxes, alice.imap_mailbox_access
Weaviate
dedup by messageId+mailboxId → direct insert into Email
Redis
RPUSH alice:mail:attachment_queue (doesn't process attachments itself — avoids GPU contention)
MQTT
pub alice/dms/done (document_type=Email) → triggers thumbnailer

alice-mail-attachment-processor

Trigger
cron 0 4 * * *
Redis
drains alice:mail:attachment_queue · shares GPU lock processor:lock:run
Writes
classified attachments → watched NAS folder (files, not DB) — re-enters the scanner pipeline as an ordinary new file

09Resolved & tracked

Follow-up from 2026-08-30 review — all four items below are now scoped into PROJ-95 (Roadmap).

Dead MQTT topics — confirmedalice/dms/error, scanner/stats, scanner/path_stats, thumb_error were debugging aids from before winston logging was adopted. No longer needed; safe to treat as dead.
alice-dms-thumbnailer never covers BankTransactionEmails get thumbnails (PROJ-93), but BankTransaction objects (no file_path, generated from a BankStatement) are never rendered. Needs the same text-rendering mode PROJ-93 gave Email, built from purpose/counterparty/amount plus a parentStatementId lookup.
alice-dms-thumbnailer-backfill drops every filePath-less objectBoth Email and BankTransaction are discarded outright, so neither ever gets a thumbnail retroactively — same root cause as above, but in the backfill path. Also missing: the processor:lock:run lock every other backfill takes, and a time-limit/auto-continue mechanism (so a run can't be started with a duration like the others). The unconnected "Split: Per collection" node (no input or output edges) should be removed while this workflow is touched.
